# Bar cache

`withBarCache(feed, options)` wraps **any** [`DataFeed`](/docs/data-feeds) in a warm-load
cache, so a custom adapter gets the same behaviour as the bundled `OpenAlgoDataFeed`. It is
a `DataFeed` in and a `DataFeed` out: nothing downstream of it changes.

```ts
import { withBarCache, OpenAlgoDataFeed } from 'openalgo-charts';

const feed = withBarCache(new OpenAlgoDataFeed(config), { ttlMs: 60_000 });

// A bar count and an end: "the last 500 bars you have at or before now".
const bars = await feed.getBars({ symbol: 'RELIANCE', exchange: 'NSE', interval: '5m', endSec, count: 500 });
// A clock window still works, and is answered as a window.
const win = await feed.getBars({ symbol: 'RELIANCE', exchange: 'NSE', interval: '5m', from, to });
```

A symbol switch and back, a timeframe flip and back, a reload, or a four-chart
[linked grid](/docs/chart-linking) opening the same series in every pane: all of those hit
the same entry instead of the network.

## Ask for bars, not for a stretch of clock

`{ endSec, count }` is the request shape this cache reasons in, and `{ from, to }` is
adapted onto it. The difference only shows on a market that closes, and then it shows
everywhere at once:

| | asks for | on a Monday morning at 1m |
|---|---|---|
| `{ from: now - 2000 * 60, to: now }` | 33.3 hours of clock | 960 bars, because a 49-hour weekend sits inside that window |
| `{ endSec: now, count: 2000 }` | 2000 bars | 2000 bars |

A window is also unable to page back **across** the closure: to reach Friday from the
Sunday open at one minute a bar you must ask for a window wider than 49 hours, and a chart
that holds 960 bars asks for a window sized to what it holds. Every drag then repeats the
same empty answer. A count has nothing to be wrong about — 144 more bars ending at the
oldest bar painted walks over the weekend by itself, because the server counts bars too.

<Callout type="info">
This is why there is **no market calendar** in here, and why you should not add one to the
host either. Weekends, a daily maintenance break, a per-product halt, ten holidays a year,
four half days, all of it tz-aware across two DST regimes that desync for three weeks every
spring: that is a second source of truth which is wrong the first January nobody updates it.
The server already knows. Ask it for a count, and read `short` when it runs out.
</Callout>

## Never serve the forming bar

A **forming bar** is the one that has not closed yet. On a 5-minute chart at 10:07, the bar
covering 10:05 to 10:10 is still being built: its close moves with every tick and is not
final until 10:10. Closed bars, by contrast, are immutable, and yesterday's daily candle
will never change again.

**A cache that serves a stale forming bar is worse than no cache at all:**

```text
10:07  Open INFY.  Fetch, last bar close 1120.  Cached.
10:08  Switch to RELIANCE to check something.
10:09  Switch back to INFY.  Cache hit, last bar close 1120.
```

INFY actually traded to 1135 while the user was away. That one wrong number then reaches the
last-price line, the price-axis tag, the header LTP, and every indicator computed off that
close: RSI, VWAP, a moving average, a Supertrend flip. With no cache the user waits 600 ms
and sees 1135, which is slower and correct. This library draws Buy and Sell buttons on the
chart, so a fast wrong price is a worse failure here than a slow right one.

So the trailing forming bar is **dropped on store**, and an entry's coverage ends at the
last bar that has actually closed. A cache hit can therefore be short by at most that one
bar, which a live subscription re-supplies immediately, and is never wrong about a bar it
does return.

<Callout type="warning">
Anything you build that computes off `bars[bars.length - 1]` inherits this rule. Keep the
completed history and re-fetch only the tail.
</Callout>

## The key deliberately excludes the range

An entry is keyed `symbol | exchange | interval`. What was requested is **not** part of the
key, and it is not stored either — coverage **is** the bars. The left edge is `bars[0]`, the
right edge is the close of the last bar, and nothing between them is claimed that is not
held:

- one entry per series holds the set that was fetched, and a **narrower** request is served
  by slicing it;
- a request the entry cannot cover refetches, and the result is **unioned** into the entry, so
  a ten-bar tail fetch extends the series instead of shrinking it to ten bars. Inside the
  window the server actually answered — its first returned bar to its last, **not** the
  requested `from`/`to` — the answer wins outright: a corrected close replaces the stored one
  and a bar the server no longer reports is deleted rather than left as a ghost. A truncated
  answer therefore cannot punch a hole through bars the server never spoke about;
- the one case that still **replaces** is a fetch separated from the entry by a band nobody
  asked about. "Adjacent" is judged on the **bar grid** and on the **ask**, not on the
  answer: a page whose last bar sits immediately before the entry's first one is adjacent
  and unions, and so is a page that *asked* up to the entry's left edge and came back with
  Friday's bars because the market was shut in between — that band was answered, and
  answered empty. A fetch that stops short of the entry with an unasked band between them
  replaces, because nothing has spoken for what is in it.

Keying on the range would miss on every pan and on every "same chart, one bar later"
reload, which is exactly the traffic a warm cache exists to remove.

## When a hit is allowed

Three tests, all of which must pass. Age is one; the other two are the ends of what the
entry actually holds, and they fail for different reasons:

| Gate | Test | Why |
|---|---|---|
| Tail freshness | `now - storedAt` is within `ttlMs`, **or** the ask ends short of the last two bar spans | A closed bar is immutable, so age alone says nothing about it. Only the recent tail can still change under you (a late print, a backend correction), so the TTL gates the tail and nothing else. |
| Left edge | The entry holds `count` bars at or before `endSec` — or, for a window ask, its oldest bar is not newer than `from` — **or** the entry is `short` | Fewer bars than you asked for is a real gap, and painting a chart that silently starts late is worse than a refetch. A market that was shut is not a gap, and only the server can tell the two apart. |
| Right edge | The ask ends before the close of the last bar held, **or** the bar after it is still forming | Nothing new can have closed, so a fetch would return the same bars. |

The right-edge gate is measured on the feed's **own bar grid** (`nextClose`), not against UTC
midnight, so a daily Indian bar opening at 03:45 UTC is judged against its own session rather
than the wrong boundary. The effect is what you want from a warm cache: yesterday's closed
session stays usable for days, while the live tail is re-read once per TTL.

A window ask is deliberately gated on its own `from` rather than on the count it implies:
a window ending at `now` always has room for one more bar than can ever be stored — the
forming one — so counting it would miss on every live request.

An entry past its TTL is **kept**, not deleted. Its closed bars are still the fastest correct
paint available, and only the request that reaches into the tail pays for a refetch — which
then rewrites the same entry. Drop one by hand with `invalidate()`.

## `short`: the server's own word for "there is no more"

An entry carries one boolean beside its bars. `short` is set when the fetch that established
the entry's **left edge** asked for more bars than it got back, and it is the only evidence
available that no older history exists.

Without it a chart cannot tell "the market was shut here" from "I have never fetched here",
and it must guess: guess one way and it refetches an identical empty answer on every drag,
guess the other and it stops paging over a gap it could have filled. With it, both are
answered by the party that knows.

It is not a one-way door — a transient shortfall (a heal mid-flight, a hole in the server's
store) must not end paging for the life of the entry — so it is cleared by:

- any later answer that establishes the left edge in full;
- a `maxBars` trim, after which the entry no longer holds the edge it was speaking about;
- `invalidate()`, `clear()` and `prune()`.

A **tail** fetch that comes back short does not set it. Being short of a window's capacity
somewhere in the middle of a session says nothing about how far back history goes.

<Callout type="info">
Out of hours a count ask is warm without any help from you: "the last 500 bars at or before
now" is a question the entry can answer whether or not the venue is open. It is only the
window shape that goes cold when nothing new can close, and the fix for that is to ask in
bars.
</Callout>

## What it actually buys you

Measured against the yfinance demo's own history endpoint, a year of daily bars:

| Symbol | Cold fetch | Payload |
|---|---:|---:|
| AAPL | 619 ms | 37 KB |
| RELIANCE.NS | 162 ms | 37 KB |

A warm hit is a slice of an array already in memory, so the round trip disappears entirely.
Where that matters:

- **Flipping symbol or timeframe and back** is the most common thing anyone does on a
  terminal, and today it re-downloads history it had seconds ago.
- **A grid stops being expensive.** Four panes are four cold fetches on load. Warm, they
  are four instant paints, which matters more once the panes are
  [linked](/docs/chart-linking) and change symbol together.
- **Fewer calls against a rate-limited broker.** A user sweeping through five symbols
  currently pays full price for every revisit.
- **Reloads can be warm too**, if you hand it a persistent `storage`. The engine will not
  pick one for you.

Be honest about the ceiling: on a 162 ms endpoint one chart feels quicker, not
transformed. The gain compounds in the grid, under rate limits, and on a slow link.

## Bounds

Capped on two axes at once, LRU-evicted on both:

| Option | Default | Bounds |
|---|---|---|
| `max` | 24 | Entries. |
| `maxBars` | 250,000 | Total cached bars across all entries. |

Entries alone do not bound memory: one intraday series can be 100,000 bars. Bar count is the
honest proxy for bytes that can be measured without serialising, and byte counting would
mean stringifying every entry on every write, which costs more than the cache saves. A
single series larger than the whole `maxBars` budget is simply **not cached**, since it would
evict everything else and then itself on the next write.

When a union pushes one entry past `maxBars`, the **newest** bars are kept: the oldest are the
ones a scroll-back can refetch cheaply. The entry's coverage start moves up with them, so a
request reaching further back misses and refetches rather than being served a series that
silently starts late.

<Callout type="warning">
**Over IndexedDB, keep `maxBars` in the low thousands.** Because a put now unions, an entry
grows until it hits the cap, and every put pays for the whole entry: one read, one merge, one
write. Measured here on a structured-clone store, a 10-bar tail put against a **50,000-bar**
entry costs **15-22 ms** and moves **4.5 MB in and 4.5 MB out** — a main-thread stall the
user feels, several times a session. The same put against a **5,000-bar** entry is **1.8 ms**
and 0.45 MB. The 250,000 default suits the in-memory `Map` it ships with, not a persistent
store; a persistent host should set `maxBars` to roughly what its charts actually paint.
</Callout>

## Options

| Option | Type | Default | Description |
|---|---|---|---|
| `ttlMs` | `number` | `300_000` | How long the tail stays trusted. Bounds only requests that reach into the last two bar spans. |
| `max` | `number` | `24` | Maximum entries. |
| `maxBars` | `number` | `250_000` | Maximum total cached bars. |
| `storage` | `BarCacheStore` | in-memory `Map` | Backing store. Sync or async. |
| `now` | `() => number` | `Date.now` | Injectable clock, for tests and for a host with a server clock. |
| `barCloses` | `(interval, barStartSec) => number \| null` | the [interval registry](/docs/custom-intervals) | When a bar that opened at `barStartSec` closes. `null` means "unknowable", and such a series is not cached at all. |
| `timezone` | `string` | engine default | IANA zone for calendar intervals, where a month is not a fixed number of seconds. |

Interval codes are resolved through the registry, which is **case-sensitive where it
disambiguates**: lowercase `m` is minutes, uppercase `M` is months. Treating a monthly bar as
a minute would make the cache believe a new bar had closed every 60 seconds.

<Callout type="info">
A code nothing recognises, and a tick or Renko series whose bars have no clock length at all,
resolve to `null` — nothing says which of their bars are complete, so they are passed straight
through, uncached, rather than guessed at. Register a
[custom interval](/docs/custom-intervals) and the cache learns it with everything else.
</Callout>

## Opting out and invalidating

```ts
await feed.getBars({ ...req, endSec, count });  // the last `count` bars at or before `endSec`
await feed.getBars({ ...req, from, to });       // a clock window, answered as a window
await feed.getBars({ ...req, noCache: true });  // always fetch, and refresh the entry
await feed.peek(req);                           // read the entry, never fetch
await feed.invalidate(req);                     // drop one series (symbol/exchange/interval)
await feed.invalidate();                        // same as clear()
await feed.clear();                             // drop everything this cache knows of
await feed.prune(7 * 86_400_000);               // drop entries older than a week, this session or not
feed.stats();                                   // { entries, bars, hits, misses, evictions }
```

## Looking before you leap

A miss inside `getBars` **is** a fetch, so it cannot express "paint what you have, I will ask
for the rest myself". `peek` can: it never fetches, never drops an entry, and never counts as
a hit or a miss.

```ts
const req = { symbol: 'RELIANCE', exchange: 'NSE', interval: '1m' };
const OVERLAP_BARS = 8;   // re-read this many bars behind the newest one we hold

const series = chart.addSeries('candlestick');
const held = await feed.peek({ ...req, endSec: Math.floor(Date.now() / 1000), count: 500 });

if (held !== undefined && held.bars.length > 0) {
  series.setData(held.bars);                       // closed bars, painted in this frame
  const tail = await feed.getBars({
    ...req,
    endSec: Math.floor(Date.now() / 1000),
    count: OVERLAP_BARS,
    noCache: true,
  });
  // Everything from `tail[0].time` is the server's truth, deletions included.
  // The overlap is what catches a late print or a corrected close at the edge
  // of what you held, so never ask for "the bars after the last one".
}
```

It returns `storedAt`, `nextClose` and `short` beside the bars, so a caller can tell a left
edge the server has run out of from one it has simply not fetched yet, and decide whether the
gap to the tail is worth stitching or a cold load is cheaper. Bars are clones, and only bars
this cache considers closed are ever in there: the forming one was dropped on store.

Two empty answers, meaning different things:

| Answer | Means |
|---|---|
| `undefined` | Nothing is stored for this series. Load it cold. |
| `{ bars: [], … }` | An entry exists, but nothing it holds is inside the window you asked for. Peek again without one to see where its bars are. |

A peek touches LRU recency — an entry you are about to extend must not be the next victim.
Nothing is written and nothing is evicted by the peek itself, but the touch **adopts** the
entry into this session's index, which is the whole point after a reload, and from then on it
counts towards `max` and `maxBars`. A later put can therefore evict something on its behalf:
a peek is free when it runs, not free afterwards.

A request that is neither `{ endSec, count }` nor `{ from, to }` passes straight through in
both directions, uncached: an open-ended ask cannot be reasoned about, because there is no
way to say what the answer was meant to contain.

## Persisting across reloads

The default store is an in-memory `Map`, and the engine will not reach for `localStorage` or
IndexedDB itself: choosing a persistence layer is the host's business, one of them is
synchronous and small and the other is asynchronous. Inject your own instead. Every store
method may return a promise, and `CachedBars` (`{ bars, storedAt, nextClose, short? }`) is
plain JSON, so it round-trips through `JSON.stringify` unchanged:

```ts
import { withBarCache, type BarCacheStore, type CachedBars } from 'openalgo-charts';

const store: BarCacheStore = {
  get(key) {
    const raw = localStorage.getItem('oac:' + key);
    return raw === null ? undefined : (JSON.parse(raw) as CachedBars);
  },
  set(key, value) { localStorage.setItem('oac:' + key, JSON.stringify(value)); },
  delete(key) { localStorage.removeItem('oac:' + key); },
  // Optional, and the only way `prune` can reach an earlier session's keys.
  keys() { return Object.keys(localStorage).filter((k) => k.startsWith('oac:')).map((k) => k.slice(4)); },
};

const feed = withBarCache(source, { storage: store, maxBars: 20_000 });
```

<Callout type="warning">
**The persisted shape changed in this release.** `CachedBars` no longer carries `from`/`to`;
coverage is the bars, plus `short`. Entries written by an older version are missing `short`
and are simply read as "not known to be short", but a host that keyed its store on a
namespace should **bump it** and let the old keys be swept — an entry whose left edge was
established by a truncated answer would otherwise be trusted a little further than it earned.
</Callout>

### Pruning what this session cannot see

`max` and `maxBars` only bound what **this** session has touched, because recency and size are
tracked in memory. An entry written last month for a symbol nobody has reopened is therefore
invisible to eviction, and it no longer expires either, since an expired entry is kept rather
than deleted. Left alone it sits in IndexedDB for ever.

```ts
await feed.prune(7 * 86_400_000);  // drop entries whose tail is over a week old; returns the count
```

`prune` walks the **store's** keys — the ones the in-memory index does not have are exactly
the ones it exists to find — so it needs `keys()` on your store. Without it, `prune` returns 0
and does nothing rather than pretending. Call it once at startup, or on a timer.

<Callout type="warning">
Recency and size are tracked **in memory**, so with a persistent store `clear()` drops only
what this session has touched. A key written by an earlier session is adopted when it is next
read — expired or not, since expiry now only forces a tail refetch — and comes under this
session's bounds from then on. A store that outlives the process is responsible for its own
overall quota, which for `localStorage` means keeping `maxBars` small.
</Callout>

## What the wrapper forwards

- `subscribeBars` and `subscribeDepth` are advertised **only when the wrapped feed has
  them**, because the codebase feature-detects `subscribeBars` to tell a history-only feed
  from a live one, and a stub that always exists would defeat that.
- Every argument is forwarded, not just the two `DataFeed` declares.
  `OpenAlgoLiveDataFeed.subscribeBars` takes a third options argument (`seedFrom`,
  `cumDayVolumeSoFar`), and a wrapper that dropped it would silently stop a live bar
  continuing the last history bar's bucket.
- Live subscriptions are never cached. Only `getBars` is.
- `feed.source` is the wrapped feed, for anything this wrapper does not forward.
- Bars are cloned on the way in and on the way out, because live builders mutate bar objects
  in place. What you get back is yours to mutate.
- A rejected fetch propagates untouched and leaves the previous entry alone: nothing is
  written unless bars arrive.

<Callout type="info">
There is no in-flight coalescing. Two `getBars` calls for the same key issued before either
resolves both reach the network, and the second one's result wins the entry. Debounce at the
call site if your UI can fire duplicate loads.
</Callout>
